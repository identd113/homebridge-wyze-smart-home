# Release notes: homebridge-wyze-smart-home 2.0.0-beta.3

The changelog is written for people installing the plugin. This page is for whoever ships and supports it: what changed in the code, the exact settings and defaults, what has been checked on real hardware and what has not, and what is known to be unfinished.

**Compared against:** `v2.0.0-beta.2` (`a7dffb5`, published 2026-08-29), the last published release. `beta.3` is `46` commits and `54` files on top of it (`+3,860 / -576` lines). Always compare against the last published release, not against the last commit or a branch.

**Pairs with:** `wyze-api@2.0.0-beta.3` (see that repository's `docs/releases/2.0.0-beta.3.md`).

## Upgrading

1. **Node.js 22 or newer.** Node 18 and 20 are no longer in `engines`. Homebridge 2.x already needs Node 22.
2. **Config is upgraded in place.** A flat (0.5.x-style) config is converted to the nested layout as before. `securityRefreshInterval`, `phoneId`, `authApiKey`, `appName`, `appVer`, `appVersion`, `userAgent`, `sc` and `sv` are now carried across; in beta.2 they were dropped on the rewrite (`src/configMigrator.js`, `PASSTHROUGH_KEYS`). `phoneId` is carried so nothing is lost, but it is not a documented setting.
3. **New cameras can appear.** Models newly recognized as cameras: Cam Pan v4 (`HL_PAN4`), Bulb Cam (`HL_BC`), Floodlight v2 (`HL_CFL2`), Doorbell v2 (`HL_DB2`). Each is a separate HomeKit accessory with its own setup code. Already paired accessories do not change. A `deviceTypeOverrides` entry for one of these models is now redundant and is skipped.
4. **Camera switch names.** New switches get function-only names. Switches that already exist keep the name they have (the legacy names are still looked up, so nothing is duplicated).
5. **Rollback:** `npm install homebridge-wyze-smart-home@2.0.0-beta.2`. beta.2 pins `wyze-api` exactly, so npm resolves the matching library. The upgraded config keeps its nested layout, which beta.2 reads.

## New settings

All under `advanced` in `config.schema.json`. Defaults are what the code uses when the field is empty.

| Setting | Default | What it does |
|---|---|---|
| `advanced.snapshotRefreshSeconds` | empty = 30 s; `0` = off | How often each camera's Home app picture is refreshed. Left empty on purpose: a stored `30` would put battery cameras on the timer. Max 3600. |
| `advanced.snapshotOnMotion` | `true` | Take a new picture as soon as Wyze's event list shows motion. |
| `advanced.warmLiveView` | `false` | Quick Live View. Opens a camera connection ahead of a live view (about 45 s, renewed by each picture request). While it is open the Wyze app cannot watch that camera. |
| `auth.totpSecret` | none | Authenticator-app secret; a fresh 2FA code on every login. Masked in the settings screen. |
| `auth.mfaCode` | none | A typed 2FA code (expires after 30 s). `totpSecret` wins if both are set. |

Not settings: `phoneId` is not supported, and `securityRefreshInterval` stays a top-level option (see the README).

## What changed in the code

### Cameras (`src/accessories/WyzeCamera.js`, `src/camera/*`)

- **Refresh scheduler** (`refreshScheduler.js`, new). With N cameras and an interval T, one camera is refreshed every T/N, in turn. Captures run one at a time with a floor of 5 s between them; with so many cameras that T/N would be shorter, each camera is refreshed less often than T and the log says how often.
- **Motion poller** (`motionPoller.js`, new). One shared `cameraGetEventsMulti` request covers every camera, every 10 s, or every 5 s when a doorbell is present. New motion on a camera queues a picture ahead of the waiting refreshes and resets that camera's own timer. A doorbell press is read from the same request.
- **Battery cameras** (`batteryModels.js`, new). Cam Outdoor, Cam Outdoor v2 and Battery Cam Pro are not put on the timed refresh (their picture is taken at startup and on motion) and never get Quick Live View, since a connection wakes them. Setting `snapshotRefreshSeconds` explicitly turns the timer on for them.
- **Quick Live View.** The Home app's picture request opens a `cameraWarmUp` connection; a live stream takes it over, and pictures come from `cameraWarmSnapshot` (the open connection's latest keyframe) instead of a new session.
- **Live start.** `prepareStream` calls `prefetchCameraConnection` so the connection details are ready when HomeKit starts the stream. A debug `timing:` line per stream shows where the time went.
- **Startup picture.** A few seconds after start, each camera fetches one snapshot, one camera at a time. Offline, off and streaming cameras are skipped; a failure is logged and never stops startup.
- **Snapshot and stream sharing.** Concurrent snapshot requests share one capture. A snapshot shows the last picture while a stream is live, and a stream waits for a capture already running. The camera model is passed to `getCameraSnapshotImage`, which removes a device-list request per capture.
- **Floodlight.** `_detectFloodlightDongle()` reads `device_params.dongle_product_model` on every update; `HL_CFL` (the Cam v3 floodlight accessory) creates a `Lightbulb` service named "Floodlight" and stores `context.floodlightDongle`, so the switch is rebuilt on every start. `spotlight` and `floodlight` both follow `P1056` (`"1"` on, `"2"` off). Log lines use `isOn()`, because `"2"` is truthy in JavaScript.
- **Names.** Default service names are function-only: Garage Door, Spotlight, Siren, Notifications, Motion Detection, Floodlight, Privacy.
- **Accessory cache (#311).** `WyzeCamera.persistState()` keeps state in memory only. Cameras are external accessories; calling `updatePlatformAccessories()` for them made Homebridge 2.x fail to serialize the whole cache.
- **Doorbell v2.** Registered as a camera and a `VIDEO_DOORBELL`. Advertised at 640x480 (4:3). No Privacy switch (`cameraSupportsPowerControl("HL_DB2")` is false).
- **devicemgmt cameras** (Floodlight Pro, Battery Cam Pro, OG, Pan v4): state comes from `cameraGetDeviceMgmtState`; a failure marks every camera service inactive.

### Other accessories

- `WyzeThermostat.js`: a separate `HumiditySensor` tile again, as in 0.5.x.
- `WyzeSwitch.js`: command grace period (`armCommandGrace(15000)`), cleared on a failed write; a poll in the window does not touch the tile.
- `WyzeAccessory.js`, `WyzeSmartHome.js`: `sanitizeDeviceName()` on every update and in the log lines (control characters removed, 64-character limit).
- `WyzeSmartHome.js`: a missing `username`, or an installed `wyze-api` below the declared range (`src/wyzeApiVersion.js`), logs one `[FATAL]` line and leaves the platform idle without touching cached accessories.

### Packaging and project

- The `src/wyze-api` submodule and `.gitmodules` are removed. For development: `npm run dev-link` (`npm link ../wyze-api`).
- Publish workflows: `npm_publish.yml` is gone; the beta and stable workflows check that a published `wyze-api` satisfies the declared range. They still use a plain `npm publish`; see "Releasing" below.
- `config.schema.json` uses `required` lists (draft 7), password masking for secrets, and trims whitespace around the Key ID and API Key.
- Repository links point at `identd113`. The `funding` entries are removed from `package.json`.

### Reporting (not shipped in the npm package)

`.github/` holds four issue forms (`bug-report`, `feature-request`, `question`, `new-device`), a chooser with links to Discussions and Discord, and `triage-issues.yml`, which runs `.github/scripts/triage-issue.js` on `new device` issues. The script labels `model:<code>` and the kind of device, skips known not-applicable models (scale, headphones, chime boxes), asks for redaction if a device name, IP address, Wi-Fi name or MAC is filled in, and counts repeat requests. It never echoes pasted values. `known-models.json` is generated from `wyze-api` (`npm run known-models`) and a test checks it is in sync.

## What has been checked, and how

### Checked on the test bridge (real cameras)

- The automatic Floodlight tile appears on a Cam v3 with the floodlight accessory, follows changes made in the Wyze app, and writes from the Home app (switched off in the Home app, confirmed off in Wyze).
- The names "Floodlight" and "Privacy" show in the Home app.
- The default log level is quiet: about 5.5 minutes at `info` produced 45 lines, nearly all Homebridge's own.
- Startup pictures: Front Doorbell (86 KB) and Back Yard Cam (712 KB), through the final build.
- The final build restarts clean: 0 errors, all 5 accessories keep both paired clients, `config.json` untouched.
- Earlier builds: Doorbell v2 snapshots and live video with audio.

### Unit tests only

Wall-switch grace period, nickname cleaning, the refresh scheduler, the motion poller, Quick Live View logic, config migration, the thermostat humidity tile, the triage script, the wyze-api version check. `npm test`: 117 pass.

### Not verified on hardware

- Cam Pan v4, Bulb Cam light, and the devicemgmt cameras (Floodlight Pro, Battery Cam Pro, OG).
- Doorbell v2: the press event, and power, siren and notification writes.
- Floodlight v2 light toggle (#264, no known fix).
- 2FA login (`totpSecret` and `mfaCode`) against a live 2FA account.
- The thermostat Humidity tile (no thermostat on the test bridge), and the setpoint units used by the library (inferred from the plugin).
- A full HomeKit live view of the final build from the Home app.

## Known issues and deferred work

- Back Yard Cam audio does not reach HomeKit; unresolved (see `wyze-api` `docs/camera-properties.md`).
- `[Snapshot] Failed for <camera>: Live view is starting` is logged at ERROR level at startup (`WyzeCameraStreamingDelegate.js`). Harmless; to be trimmed.
- HAP "ConfiguredName" warnings at startup, from `_getOrAddService`.
- A live view that starts while a warm connection is hung waits for it.
- The warm-connection close at shutdown is not awaited.
- The event window of 20 is shared by the doorbell and the motion check.
- The floodlight flag is never cleared if the accessory is removed from the camera; the sibling switches can disagree until the next poll.
- A warm session with no usable keyframe can leave the picture frozen.
- Three near-duplicate walkers of the STAP-A response in `wyze-api`.
- `WyzeSwitch` reads `switch-power` with `!!value`; a string `"0"` would read as on. Not seen in practice.
- `getHmsID()` in `wyze-api` returns the raw plan list (documented that way).
- The meaning of property `P1048` is unconfirmed (assumed sound-event recording; set back to 0 on the test camera).
- The `wyze-api` wiki repository does not exist yet, so the wiki sync workflow fails.

## Releasing

1. Release `wyze-api@2.0.0-beta.3` first: the plugin's publish workflow refuses to run unless a published `wyze-api` satisfies `^2.0.0-beta.3`.
2. The `NPM_TOKEN` secret is a stage-only token. `wyze-api`'s workflows use `npm stage publish` and the version is approved on npmjs.com with 2FA. The plugin's workflows still use a plain `npm publish` and need the same change before they can publish with that token.
3. Create a GitHub release with **Pre-release** ticked, targeting `2.x`, tag `v2.0.0-beta.3`.
4. Verify: `npm view homebridge-wyze-smart-home dist-tags` shows `beta` at `2.0.0-beta.3` and `latest` still at `0.5.61`; then a clean `npm install homebridge-wyze-smart-home@beta`.
5. Turn on Issues and Discussions on the repository, and create the `new device` label, so the forms and the chooser work.
6. The `wyze-api` dependency is a range (`^2.0.0-beta.3`) on purpose, so a new install of the plugin picks up the newest `wyze-api` that fits. That lets a library fix ship without a new plugin release, and it has three consequences:
   - Before publishing a new `wyze-api` beta, run this plugin's `npm test` and a live check against it, because new plugin installs will take it.
   - Existing installs keep the library they have until the plugin is reinstalled or updated.
   - If a `wyze-api` version turns out to be broken, publish a fixed one with a higher number, run `npm deprecate wyze-api@<bad version> "<reason>"`, and raise the floor in this `package.json` to the fixed version.
